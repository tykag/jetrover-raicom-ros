## 4. 导航关键故障：麦克纳姆误用差速模型

小车是：

```text
MACHINE: JetRover_Mecanum
```

但本次及旧脚本启动导航时没有传 `drive_type`：

```bash
roslaunch hiwonder_navigation navigation.launch map:=explore robot_name:=/ master_name:=/
```

`navigation.launch` 默认值却是：

```xml
<arg name="drive_type" default="diff-corrected"/>
```

该值同时传给：

- AMCL 的 `odom_model_type`
- TEB 局部规划器的运动学参数

因此麦克纳姆底盘一直按差速底盘定位和规划。实车现象正好是：

1. 静止时注入 `park1` 初值后，激光看起来能与地图重合。
2. 一移动，AMCL 协方差迅速放大并可能跳到地图中的相似区域。
3. `move_base` 接受目标，但长时间保持 `ACTIVE`。

下次必须显式启动全向模型：

```bash
roslaunch hiwonder_navigation navigation.launch \
  map:=explore robot_name:=/ master_name:=/ drive_type:=omni
```

这是高置信度根因，但**修正后尚未实车复测**，不能写成已经解决。

## 5. `park1` 不能同时当导航点和作业点

当前 `raicom_waypoints.yaml`：

```yaml
park1:
  x: 2.4564735657111436
  y: 0.400469059255336
  yaw: -1.6464750625536042
```

该坐标来自方块成功放置时的车位，应该保留为精确作业位，建议改名
`park1_place`，不要删除。

实测把它直接发给 `move_base`：

- 小车会向园区一靠近；
- 用户判断离台子过近；
- 40 秒仍未判成功，保护逻辑已取消目标并发零速度。

自动化应拆成两段：

```text
park1_approach（离台安全的全局导航点）
  → 雷达/视觉局部低速对位
  → park1_place（昨天已验证的放置作业位）
  → place_low
```

这样只需各标定一次，不是每次运行重新记位置。全局导航误差由最后局部对位消除。

当前还没有标定 `park1_approach`，也没有实现园区局部对位。`raicom_auto.py`
仍会把 `park1` 直接当导航终点，因此自动模式必须保持禁用。

## 6. AMCL 实测记录

在已知位于园区一时注入 `park1` 初值：

- 原地连续转动后曾收敛到约 7 cm / 6.4°；
- 使用较小初始协方差并短距离后退后，曾达到约 14 cm / 8°；
- 但在错误的 `diff-corrected` 模型下继续移动后再次发散到约 0.5–0.8 m / 50°；
- 手柄转整圈时还曾跳到地图中的错误相似区域。

所以不要把“静止截图中激光贴墙”当作导航可用的充分条件。必须在 `omni` 模型下做
“前后移动 → AMCL 连续跟踪 → 导航短距离返回”的完整验证。

## 7. 运行环境和安全

车上默认终端是 zsh，使用：

```zsh
source ~/ros_ws/devel/setup.zsh
export ROS_MASTER_URI=http://127.0.0.1:11311
export ROS_IP=127.0.0.1
unset ROS_HOSTNAME
export OPENBLAS_CORETYPE=ARMV8
```

不要在 zsh 中 `source setup.bash`，会出现 `/home/hiwonder/setup.sh` 找不到的提示。

Python 3 漏掉 `OPENBLAS_CORETYPE=ARMV8` 会在导入部分 ROS/actionlib 模块时直接
`Illegal instruction`，表现为 SSH 会话返回 `-1`、脚本第一行日志都没有。

所有导航测试结束时均已取消目标并发送零速度。最后物理位置经过多次手柄和导航移动，
**下次开机不要假定仍精确位于 `park1`**。
